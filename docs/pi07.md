# π0.7-Style Training

This repository implements the main training ideas of π0.7 on top of π0.5. All of them can be combined, and all of them
start from the public `pi05_base` checkpoint.

| Feature | Where | Docs |
|---|---|---|
| Episode metadata prompting (speed, quality, mistake, subtask) and classifier-free guidance | `DataConfig.episode_metadata` | [episode_metadata.md](episode_metadata.md) |
| RECAP: value function and advantage-conditioned policy | `ValueConfig`, `scripts/compute_advantages.py` | [recap.md](recap.md) |
| Subgoal images | `DataConfig.subgoal` | [subgoal.md](subgoal.md) |
| Training-time real-time chunking | `Pi0Config.rtc_max_delay` | below |
| Memory (past frames) | `Pi0Config.history_frames` | below |
| Knowledge insulation | `Pi0Config.knowledge_insulation` | below |
| High-level policy that predicts the next subtask | `SubtaskPolicyConfig`, `DataConfig.subtask_targets` | below |

All features are available in JAX (`scripts/train.py`) and PyTorch (`scripts/train_pytorch.py`, multi-GPU with DDP,
see [pytorch_training.md](pytorch_training.md)).

`pi05_libero_pi07` combines all the low-level policy features, and `subtask_libero` is the high-level policy. Both are
in `src/openpi/training/config.py`. The configs for the SO101 arm are described in [so101.md](so101.md).

What is **not** included:

- The π0.7 weights and data.
- The Gemma 3 4B backbone, the 860M action expert, and the 14B world model that generates subgoal images.

## Training-time real-time chunking (RTC)

The policy predicts the next chunk while the current one is still being executed. The actions executed during the
inference delay are already fixed, so the new chunk has to continue them smoothly.

**Training.** With `rtc_max_delay=d`, each example samples a delay in `[0, d]`. The first actions of the chunk, up to
that delay, are given as clean actions with flow time 0 and are excluded from the loss. Set `d` to the maximum inference
latency in control steps. For example, π0.7 uses 12 steps, which is 240 ms at 50 Hz.

**Inference.** Pass the committed actions in the `actions` key of the observation, in the same space as the actions
your robot runtime executes. The returned chunk starts with these actions, so start executing from that index.

```python
chunk = client.infer(obs)["actions"]
...
# While executing chunk[t], request the next chunk. The actions chunk[t : t + delay] will be executed before it arrives.
next_chunk = client.infer({**obs, "actions": chunk[t : t + delay]})["actions"]
# next_chunk[:delay] == chunk[t : t + delay]; continue with next_chunk[delay:].
```

## Memory (past frames)

With `history_frames=K`, each camera also gets the K previous frames, sampled every `history_stride_s` seconds
(default 1 s).

- **Encoding.** The past frames are encoded with the same vision encoder. They are compressed into the tokens of the
  current frame with a learned temporal embedding and masked pooling, followed by a projection. So the number of tokens
  does not grow with K.
- **Initialization.** The added term is gated by a parameter initialized to zero, so the model starts out exactly as
  π0.5.
- **Dropout.** During training, the whole history is dropped with probability `history_dropout` (default 0.3).

The new parameters are not in `pi05_base`. Load the checkpoint with:

```python
CheckpointWeightLoader("gs://openpi-assets/checkpoints/pi05_base/params", missing_regex=".*lora.*|.*history_.*")
```

At inference, pass the past frames in the `history` key as a list (oldest first) of dicts with the same image keys as
the observation:

```python
client.infer({**obs, "history": [{"observation/image": img_t2, "observation/wrist_image": wrist_t2},
                                  {"observation/image": img_t1, "observation/wrist_image": wrist_t1}]})
```

If fewer than K frames are passed, the missing ones are masked out.

This is a simplified version of the MEM encoder. The proprioceptive history is not used.

## Knowledge insulation (KI)

With `knowledge_insulation=True`, two things change during training:

- The prompt is followed by the FAST tokens of the action chunk, which the backbone learns to predict with a
  cross-entropy loss.
- The action expert only sees stop-gradient keys and values of the backbone. So the flow matching loss trains the action
  expert, and the backbone is trained by the discrete loss only.

The FAST tokens are attended to by no other token, and the positions of the following tokens are the same as without
them. So inference is unchanged: only the flow matching action expert runs.

According to the paper, KI trains faster and preserves the language understanding of the backbone better. It costs
about 20% more compute per step.

Two requirements:

- `max_token_len` must leave room for the FAST tokens. The FAST tokenizer (`physical-intelligence/fast`) is downloaded
  from Hugging Face on first use.
- `ki_max_fast_tokens` (default 128) limits the number of decoded positions, to save memory.

## High-level policy

The high-level policy predicts the next subtask from the images, the task and the previous subtasks. It uses the
pi0-FAST architecture and is initialized from `pi0_fast_base`. It is trained on the subtask segments of the
[annotations file](episode_metadata.md), via `DataConfig.subtask_targets`.

A good way to collect this data is verbal coaching:

1. Run the low-level policy and type the subtasks for it step by step.
2. Record them as segments.
3. Train the high-level policy on them.

At inference, run both policies, for example on two policy servers:

```python
previous = []
while not done:
    subtask = high_level.infer({**obs, "prompt": task, "previous_subtasks": previous})["subtask"]
    if not previous or previous[-1] != subtask:
        previous.append(subtask)
    actions = low_level.infer({**obs, "prompt": task, "subtask": subtask})["actions"]
```
